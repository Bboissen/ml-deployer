    AWS login for an existing console identity

    From the PR28 checkout, choose a named non-default profile and complete browser sign-in/MFA. Replace my-workspace with your chosen profile name.

    bash scripts/aws/workspace.sh login --profile my-workspace --region us-east-1
bash scripts/aws/workspace.sh auth-check --profile my-workspace --region us-east-1

    Use a permitted non-root operator. CLI/SDK principal comparison exists; backend/provider checks remain part of foundation/saved-plan preflight. Successful login does not grant infrastructure permissions or authorize deployment. AWS login and compatibility.

    AWS IAM Identity Center 
    bash scripts/aws/workspace.sh login --profile my-workspace --region us-east-1 --method sso
bash scripts/aws/workspace.sh auth-check --profile my-workspace --region us-east-1

    The setup wizard needs your organization's start/issuer URL and directory region, then lets you choose an authorized account/role. This login is supported by AWS; this repo still needs generalized role-based terminal/job grants before claiming its SSO journey is accepted. Official SSO instructions.

    GitHub access 
    bash scripts/aws/workspace.sh github-login

    Public clones do not need GitHub authentication. Private access needs your authorization. The current VM path uses a read-only SSH deploy key in Secrets Manager; a workstation GitHub login does not automatically authenticate the VM. The configurator must wire that separate access route.     Supported hosts and installer acceptance

    Linux: glibc ≥ 2.35, x86_64/arm64; Ubuntu 22.04/24.04 and Debian 12/13 are reference distributions. Missing native Git/OpenSSH/curl/unzip utilities can be installed through setup --system-packages on Ubuntu/Debian, with your sudo password when needed. macOS: 13+, Intel/Apple Silicon, with Apple Command Line Tools. Alpine/musl and Windows are unsupported.

    Clean Linux x86_64 installation, rerun and check-only passed. Native macOS and Linux arm64 installation plus real browser login still need acceptance; offline platform checks are not native proof. Managed tools are selected only for controller commands; host installations and shell startup files are preserved.

    Remaining work, in implementation order

    M0 baseline is recorded. M1 short configuration and M2 tools/login have source milestones in PR27/28; full discovery, grants and native platform acceptance remain. The next source task is foundation/access onboarding, reusing the existing roots and guarded Python engine.

    1. M3 + remaining M1: foundation, identity and repository access
      • Generalize account/project/operator bindings in roots and scope validators together. Keep the reviewed region/image profile; discover eligible RAM-first capacity and estimated costs, with an optional chosen price ceiling.
      • Drive separate bootstrap/platform roots; capture outputs automatically. Reuse only after exact identity, ownership, state lineage and guard checks. Never adopt a resource just because its name matches.
      • Use public HTTPS without credentials. For private GitHub, register a project-scoped read-only deploy key when permitted, store it through the existing secret route and keep private keys out of plans/state/logs. Add portable RAM-backed key handling for macOS.
      • Pass when: no manual ARNs/hashes/secret versions; interrupted onboarding reconciles state; an unrelated resource or unsupported grant stops before compute.
    2. M4: ingestion before compute
      • Separate adapters for confirmed local files/directories, S3 and public HTTPS. No private remote platform or cross-cloud transfer in the first release.
      • Stream bounded transfers; seal a manifest with paths, bytes, checksums and native object versions. Reject changed local files and mixed snapshots. Reuse verified completed objects; handle or abort only operation-owned incomplete multipart uploads.
      • Show source/destination, transfer limits and fees in the scope. Failed ingestion must launch no VM and must not delete unrelated objects.
      • Pass when: multi-file inputs, spaces, changed files, interruptions, checksums and a non-sensitive file above the old 1 MiB fixture bound are covered. Use bounded tests and remove their owned payloads afterward.
    3. M5: ordinary project setup, execution and outputs
      • Reuse exact-revision checkout and non-root execution. Run the external repository's explicit setup and run argument arrays on every job Deploy; never execute it locally to guess commands.
      • Persist only declared output paths and bounded logs. Replace mandatory fixture hashes with separate infrastructure, setup, job, output-transfer and cleanup outcomes; keep tiny deterministic assertions in acceptance tests.
      • Pass when: two small repositories with different entrypoints run without source edits or pre-known output hashes; setup failure, timeout and failed output transfer remain distinct from cleanup success.
    4. M6: one Deploy, status and recovery
      • Compose configuration → scope review → foundation/access → ingestion → guard/launch → execution → output verification → teardown. Bind every inspected immutable plan to the existing task authorization.
      • Add a durable operation journal, workspace lock and bounded status/logs/cancel/resume. Reconcile exact remote ownership after interruption; never retry an uncertain launch blindly.
      • Keep the provider expiry guard through partial failures and controller loss. Scope expansion or persistent-resource deletion needs a new decision; routine stages do not.
      • Pass when: no manual generated-file edits, no repeated routine prompts, no duplicate VM after retries, and an exact recovery instruction for partial/unknown outcomes.
    5. M7 + remaining M2: native acceptance and distribution
      • Accept clean Linux and macOS install → browser authentication → project configuration → review → job → retained results → verified teardown. Record the exact architectures and operator identities tested.
      • Repeat using retained data; cover public/private repos and the supported source routes. Keep offline/mocked checks routine and native trials separately bounded and authorized.
      • Publish versioned release artifacts with integrity metadata and a first-download quickstart, replacing manual source checkout. Clean all owned test images, volumes, caches, temporary runtimes and payloads after each trial.
      • Pass when: the journey needs no author's absolute paths, credentials or historical receipts. GCP/Azure and hosted/browser execution remain later independent work.
    Decisions already settled: AWS first; Linux and macOS; job mode runs declared dependency setup and entrypoint on every Deploy; local/S3/public HTTPS ingestion first. Continue improving Python, use Bash for initial installation, and retain OpenTofu. Recommended private access: the existing read-only deploy-key route. A browser controller and GitHub App are later options.

    Needed for the first live trial: an explicit permitted AWS profile/account, selected project/repository/ref, non-sensitive dataset, output paths and reviewed cost/lifetime limits. These are concrete deployment inputs, not blockers for the next source milestone.
