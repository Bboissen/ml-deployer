Tools and authentication

The first installer release must support Linux and macOS. It will install pinned tools and verify downloads; supported distribution, OS and architecture versions will be declared and tested. The current guest installer is not yet a workstation installer.

AWS login for an existing console identity

After AWS CLI installation, choose a named profile and complete browser sign-in. These are existing AWS commands, independent of the proposed configurator.

aws login --profile my-workspace
aws sts get-caller-identity --profile my-workspace

Use a permitted non-root operator. Login permission and resource-creation permission are distinct. The installer must verify the pinned CLI, SDK, OpenTofu provider and state backend use the same identity. AWS login and compatibility.

AWS IAM Identity Center 
aws configure sso --profile my-workspace
aws sso login --profile my-workspace
aws sts get-caller-identity --profile my-workspace

The setup wizard needs your organization's start/issuer URL and directory region, then lets you choose an authorized account/role. This login is supported by AWS; this repo still needs generalized role-based terminal/job grants before claiming its SSO journey is accepted. Official SSO instructions.

GitHub access 
gh auth login --web --git-protocol https
gh auth status

Public clones do not need GitHub authentication. Private access needs your authorization. The current VM path uses a read-only SSH deploy key in Secrets Manager; a workstation GitHub login does not automatically authenticate the VM. The configurator must wire that separate access route. AWS CLI, OpenTofu, Git, the existing Python operator runtime and required utilities; optionally GitHub CLI and the Session Manager plugin. It must preserve existing tool installations, profiles and credential stores, and support safe reruns. Cloud provisioning is a subsequent explicit Deploy operation.

Build on the working AWS lifecycle

  1. Baseline and configuration. Start from merged main, remove hardcoded account/project assumptions and generate internal fields.
  2. Linux and macOS onboarding. Ship a repeatable installer, login assistant and field guide.
  3. Foundation and repository access. Automate first-use setup and verified reuse without copying ARNs or hashes.
  4. Dataset ingestion. Stream local/S3/HTTPS sources, preserve manifests, resume transfers and reuse retained data.
  5. Generic execution. Automatically run declared setup/entrypoint; remove mandatory pre-known ML result hashes.
  6. One Deploy and recovery. Compose stages, give bounded status and reconcile interruptions without duplicate launches.
  7. Clean-host acceptance and releases. Verify both supported host families and the complete AWS journey.
  8. Optional extensions. GitHub Actions/OIDC, then independently accepted GCP/Azure adapters.

Recommended implementation: a thin Bash installer and CLI interface around the current Python/AWS controller. A Go frontend is possible later; a controller rewrite is not required.
