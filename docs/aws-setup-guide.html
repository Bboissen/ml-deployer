AWS workspace: first-use guide

Run make in the repository folder and answer its setup questions. It prepares the tools, creates your project configuration, and offers native sign-in. This companion shows progress; the setup work happens in the same terminal.

No live readiness. Run make (or ./workspace guide) in the repository folder and open the address it prints to see which steps are done. Opened as a file, this page is a plain checklist.

JavaScript is off or unavailable: readiness is not shown, every public and private variant is listed, and commands can be selected and copied by hand.

  1. Get the source and run make

    git clone https://github.com/Bboissen/Ray_terraform.git
cd Ray_terraform
make            # or ./workspace guide when make is not installed

    make prepares hash-pinned AWS CLI, OpenTofu, Python and Session Manager builds in the repository's ignored .tools/ folder (about 600 MB), then asks for your project settings. Sign-in uses the native provider's browser flow. Keep that terminal running; Ctrl+C stops setup and the companion. Deployment still requires review and confirmation of its exact scope.

    Laptop connecting over SSH: keep the repository on the server. From your laptop, connect with port forwarding, then run make in the server checkout:

    ssh -L 8765:127.0.0.1:8765 homelab
# Now on the server:
cd /path/on/server/Ray_terraform
make

    Open the printed http://127.0.0.1:8765/ link in your laptop's browser. The SSH tunnel carries the server's page to your laptop. Keep this terminal running and use a second SSH terminal for setup steps. No laptop clone, launcher or cloud tools are needed.

    If make is already running in an SSH session, leave it running and add the tunnel from another laptop terminal: ssh -N -L 8765:127.0.0.1:8765 homelab. Keep that terminal open too. A command running only inside SSH cannot open the laptop browser automatically. Under SSH the guide keeps its selected port fixed; stop an older guide if that port is busy.

    Ubuntu/Debian: if this step says system packages are missing, run ./workspace setup --system-packages (uses sudo only to add missing curl, unzip, tar or dpkg), then make again. macOS: if Git is missing, macOS first offers the Command Line Tools dialog. Supported: Linux with glibc (x86_64 or arm64) and macOS (Intel or Apple Silicon).

  2. Configure your project

    Answer the questions in the terminal running make. It creates the folder and saves a validated project file for you. Press Enter to keep a suggested value. Provide your real repository and dataset source; credentials are entered only through native sign-in.

    Fields to editUse your own values
    profile, project, workspaceYour AWS login profile and names for this project and workspace.
    dataset.sourceYour existing dataset path or supported remote source; the example's ./dataset must exist beside the project file if you keep it.
    repository.url, repository.refYour ML repository URL and branch, tag or commit; owner/project.git is a placeholder.
    commands.setup, commands.run, outputs.pathsThe commands and output folders that your ML repository actually uses.
    maximum_runtime_minutesA limit from 15 to 60 minutes.
    Manual configuration reference (optional) 
    mkdir -p ~/aws-workspace/demo
cp infra/aws/project.example.json ~/aws-workspace/demo/project.json
"${EDITOR:-nano}" ~/aws-workspace/demo/project.json

    The guide checks ~/aws-workspace/demo/project.json; for another location stop it and start it with make PROJECT=/path/project.json. Field reference: project configuration. The reviewed CPU profile currently supports us-east-1.

  3. Sign in to AWS

    make offers sign-in using the profile you chose. Accept that prompt to continue in the same terminal. Over SSH it uses remote login and prints the native browser link for your laptop. The controller never sees or stores a password or key.

    ./workspace login --profile my-workspace --region us-east-1

    Add --method sso for IAM Identity Center and --remote when the browser is on another device (it prints a link, then you paste the code the browser shows back into the terminal). A successful login does not prove permission to create infrastructure; Deploy checks that against the exact saved plans. Static access keys are refused; shell defaults such as AWS_PROFILE are ignored in favour of the profile in your project file.

    Browser shows “400 Bad Request” or another sign-in error? Each sign-in link works once and only for a few minutes, and only while the login command is still waiting in the terminal. Close that tab, press Ctrl+C in the terminal, run the login command again and use only the page it opens now; never reuse an older link. If it still fails, rerun with --remote.

  4. Connect private GitHub access only when needed

    Public repository

    Nothing to do. Use the HTTPS URL, for example https://github.com/owner/project.git. No GitHub login is required anywhere.

    Private repository

    Use the SSH URL, for example git@github.com:owner/project.git, install the managed GitHub CLI and log in once. You need admin permission on that repository: Deploy registers a read-only deploy key for it and stores the private key only in AWS Secrets Manager.

    ./workspace setup --github
./workspace github-login

  5. Review and Deploy

    When every step above is done, the first command resolves the account, zone, repository commit, dataset bytes, machine size, price estimate, retained resources and lifetime into one immutable scope, prints it, and asks once. Type deploy to launch exactly that scope; press Enter to stop with no cloud change.

    ./workspace ~/aws-workspace/demo/project.json
./workspace ~/aws-workspace/demo/project.json status --wait 30

    For automation, pass --authorization 'Approve the displayed scope' instead of the prompt; nothing launches without one of the two. Stage progress (artifacts, foundation, repository, ingestion, prepare, launch, job, verify, cleanup) prints as it happens. Every saved OpenTofu plan is still inspected and bound to that one authorization; no ARN, hash or state path is copied by hand. A changed file or source needs a new review.

  6. Locate output and confirm compute cleanup

    The outcome lists infrastructure, setup, job, output persistence and cleanup separately. outputs is the S3 location of your declared output paths; compute cleanup: success together with outputs verified after compute deletion: True means the machine, disk and network interface are gone and your results are still readable.

    ./workspace ~/aws-workspace/demo/project.json status
./workspace ~/aws-workspace/demo/project.json logs

    Both print output_uri, the s3://…/output/ prefix holding your declared paths and bounded logs; browse it in the S3 console or with your own AWS CLI. Retained on purpose: the dataset and output buckets, the separate state bucket, the no-ingress network, IAM boundaries and the expiry guard. They can continue to cost money; deleting them is a separate reviewed decision. A second Deploy with the same data verifies and reuses the retained versions without uploading again.

Installation failed: repair and retry

Something is broken or half installed. Rebuild the managed tools; logins, project files, shell settings, state, saved plans and operation evidence are untouched, and the previous tools stay selected if the rebuild fails.

./workspace setup --fresh
./workspace doctor ~/aws-workspace/demo/project.json --debug

If setup stops with install.lock: a setup that exited is recovered automatically; a running setup is reported with its process ID. Only when the message says the lock has no verifiable owner and you are sure nothing is running anywhere, remove the exact directory it names.

The launcher itself is broken. Source checkout: git status, then git checkout -- workspace scripts restores the tracked files. Published release: rerun the same version's install.sh --restore; it verifies the archive checksum, puts back only changed release files and keeps evidence, tools and older versions.

A Deploy was interrupted. That is not an installation problem. Run ./workspace project.json resume (reconciles owned resources, never repeats a launch) or cancel. Fresh setup never touches operations.

What is and is not accepted yet

The complete install → login → configure → Deploy → retained reuse journey has offline, mocked coverage and a clean Ubuntu container install without preinstalled Python. Native acceptance still pending for the generic journey: a clean macOS and Linux arm64 install with real browser login, a real generic job with durable outputs, retained-data reuse against the live account, controller-loss drills and verified teardown. One bounded private SSH/Make job passed natively earlier. Details and the exact authorization needed: native acceptance scope.
