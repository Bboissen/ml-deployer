Minimal multi-cloud ML infrastructure

One contract, three independent provider implementations, one disposable runner per state.

This page explains structure only. OpenTofu code, lock files, external saved-plan evidence, and fresh provider CLI output are authoritative for actual state.

One run from request to receipt

1. ML input

OCI repository + immutable SHA-256 digest and opaque run-spec bytes.

→

2. Review

Closed request, backend binding, saved plan, and exact authorization.

→

3. Runner

One VM runs once, writes its isolated outputs, and stops at a provider deadline.

4. Local handoff

The workload leaves bounded log and local receipt evidence. It cannot declare trusted success.

→

5. Trusted receipt

An unattached control identity verifies provider facts and conditionally creates the final receipt.

→

6. Destroy

Runner compute, identity, deadline, disk, NIC, and address disappear; durable evidence remains.

Three state roots per provider

bootstrap

Creates only the protected remote-state backend. Bootstrap retains local state.

platform

Persistent storage, registry, trusted publisher, and the provider network boundary.

runner

One disposable VM plus deployment identity, grants, disk, outbound address, and deadline.

Why there is no Tailscale

No inbound service

Normal runners need object storage and registry egress, not a persistent application network.

Native operator tools

SSM, IAP, and Run Command avoid public SSH and another credential/control plane.

Durable state is elsewhere

Inputs, outputs, logs, receipts, and OpenTofu state live in provider storage.

Routine local gate

make check runs repository, contract, conformance, provider-root initialization/validation, policy mutation, and formatting checks. It disables backends and never applies infrastructure.

Cloud mutation starts only after provider CLI scope checks, a reviewed saved plan, and authorization for that exact plan digest.
